# 实现笔记

几个实现细节放在这里，读代码或接入自己的场景时可以对照着看。

## 代码放在哪里

| 模块 | 职责 | 对外边界 |
| --- | --- | --- |
| `src/math.rs` | 列主序矩阵乘法、TRS 合成、输入归一化 | Rust 内部纯计算函数 |
| `src/lib.rs` | 场景拓扑、局部变换、世界矩阵、JS 导出 | wasm-bindgen 类与数组函数 |
| `src/renderer.rs` | WebGL2 状态、GPU 资源、实例化绘制 | `RustRenderer` 构造、渲染和释放 |
| `web/scene.js` | 固定种子数据、Three.js 对照实现、矩阵视图 | 两条计算路径共享输入 |
| `web/main.js` | 页面状态、相机、后端选择与帧循环 | 用户交互、渲染调度 |
| `web/benchmark.js` | 预热、交替采样、统计与报告 | 可导出的计时结果 |

场景数据由 WASM 模块管理。演示里的相机、控制器和几何体来自 Three.js，接入时也可以换成自己的输入。

## 节点怎么存

`SceneGraph` 包含四类连续数组：

| 字段 | 数据内容 | 每节点有效载荷 |
| --- | --- | --- |
| `parents` | `i32` 父节点索引，`-1` 表示根 | 4 字节 |
| `transforms` | 位置 xyz、四元数 xyzw、缩放 xyz | 40 字节 |
| `order` | 父节点先于子节点的 `usize` 索引序列 | wasm32 下 4 字节 |
| `worlds` | 16 个 f32 的世界矩阵 | 64 字节 |

wasm32 下，每个节点的这部分数据占 112 字节，10,000 个节点约 1.12 MB。这个数字只算表里的数组，不含分配器开销、构造时的临时数据、JS 对象和 GPU 缓冲。

同一节点的 TRS 放在一起，世界矩阵另存一份连续数组。场景创建后节点数量固定，所以索引不会变化，修改 TRS 也不用重新分配矩阵数组。

使用 f32 可以直接对应 GPU 的矩阵格式，但精度低于 JS Number。差分测试允许一定的绝对和相对误差；坐标特别大时，需要另外考虑精度问题。

## 更新父子节点

构造场景时，先把根节点加入队列，再沿着父子关系把子节点追加进去。这样得到的顺序保证父节点先于子节点。如果最后没有遍历到全部节点，就说明存在循环，构造会返回错误。

因此父节点不必排在数组前面。计算顺序需要 O(N) 时间和临时空间，之后每帧直接使用 `order`，不用递归。

每帧按顺序执行：

1. 从局部 TRS 合成 `local = T × R × S`。
2. 根节点令 `world = local`。
3. 子节点令 `world = parentWorld × local`。
4. 将结果写入 `worlds[id × 16 .. id × 16 + 16]`。

每次更新会重算全部节点，复杂度为 O(N)。静态对象多的时候，这里还有优化空间：可以加脏标记，但父节点变化时必须连同后代一起更新。

`reparent()` 先在副本上检查新的父子关系，成功后才写回。`set_transforms()` 也会先检查长度、数值和四元数，再替换数据。输入有问题时，原来的场景还能继续用。

## JS 和 WASM 之间的数据

可以按调用频率选择接口：

- 单次数学调用适合功能验证和低频使用，输入与输出经绑定层复制。
- 批量数学调用在一次边界调用中处理多组矩阵，仍包含数组复制。
- `SceneGraph` 将长期数据保存在 Rust 内，JS 每帧只发出计算指令，再按需要读取结果。

矩阵输出提供复制与借用两种方式。`world_matrices()` 返回可以长期保存的副本；`matrices_ptr()` 和 `matrices_len()` 允许 JS 在当前 `wasm.memory.buffer` 上建立 Float32Array 视图。

借用视图要注意两件事：WASM 内存增长后，需要重新建立视图；场景释放后，旧视图不能再用。混合模式每帧重新取一次视图，再写入 Three.js 的实例矩阵数组。这里只省掉一份中间副本，写入 Three.js 和上传 GPU 的成本仍然存在。

## 渲染和资源释放

Rust 渲染器拥有一个 shader program、一个 VAO，以及四个 buffer：顶点、索引、实例矩阵、实例颜色。几何体和颜色在构造时上传，矩阵缓冲按实例数量预分配，每帧通过 `bufferSubData` 更新。

顶点属性的位置固定：position 使用 0，instanceMatrix 使用 1–4，instanceColor 使用 5。Rust 和 Three.js 共用同一份 GLSL，方便检查两边画出来的结果。

调用 `render()` 前要先更新场景矩阵。用完后调用 `free()`，Rust 的 `Drop` 会删除 GPU 资源。页面退出、切换对象数量时也会释放旧对象；构造中途出错时会清理已经创建的资源。

窗口或容器尺寸改变时，仅在宽高均大于零的情况下更新相机投影和绘图缓冲。布局暂时归零时保留上一次有效投影，避免后续产生 Infinity 或 NaN。WebGL 上下文丢失当前通过错误提示处理，需要刷新重建。

## 跑分测了什么

JS 与 Rust 使用相同种子生成的 Float32 输入。场景矩阵对照采用真实 Three.js Object3D；测试同时提供只更新、更新加输出、批量乘法、逐个乘法和函数调用五种工作负载。

每项先预热，再交替跑 JS 和 Rust，收集七轮样本并取中位数。如果某一边的中位数为零，就不计算倍数，页面会显示低于计时精度。

这些指标测量 CPU 墙钟时间。当前没有 GPU 完成计时，不能将绘制提交时间解释为整帧 GPU 时间，也不能将单次运行的倍数推广到其他设备。f32 与 JS Number、数据布局、JIT 内联和数组传输均可能影响结果。

## 后面可以补什么

先补节点增删和脏标记，再考虑可见性过滤和多几何体批次。SIMD、Worker 和 GPU 计时也可以继续试，目前都还没有实现。

改计算逻辑时，用 Three.js 校验结果；改内存接口时，检查内存增长和对象释放；改渲染时，检查实际像素。跑分结果里则继续保留输入规模、精度和计时范围，方便前后比较。
